Install

No git clone, no npm install, no plugin system — just curl/tar, or PowerShell.

macOS · Linux · git-bash · WSL 
curl -fsSL https://raw.githubusercontent.com/DMK980/Blueprints/main/install.sh | bash -s -- backend
Windows PowerShell 
iwr -useb https://raw.githubusercontent.com/DMK980/Blueprints/main/install.ps1 -OutFile install.ps1
.\install.ps1 backend
[destination]
Install somewhere other than ./backend — e.g. ... -- backend ./server (bash) or .\install.ps1 backend .\server (PowerShell).
--force / -Force
Overwrite the destination if it already exists. Without it, the installer refuses rather than clobbering a folder that's already there.
No script?
Copy the backend/ folder out of this repo yourself. The installer is a convenience, not a requirement.

Usage

Everything after install happens inside a coding-agent session. You never edit these files yourself.

1

Start a session in the installed project

In Claude Code, that's it — it auto-loads backend/CLAUDE.md, which pulls in the full procedure. Any other coding agent: tell it to follow the instructions in backend/AGENTS.md.

2

The interview runs in a fixed order

INTERVIEW.md asks the product description and its defining mechanism first, then roles, money, and LLM use, then each file under rules/ in the order that keeps every cross-reference pointing at something already answered — data model, then business logic, then auth, then routes, then security, and only then the stack, deliberately last, once your actual requirements are known instead of guessed.

3

Every file gets rewritten with real content

Each rules/*.md file's "Questions to answer" gets replaced with concrete, product-specific rules and the reasoning behind them — not generic best-practice filler. llm-integration.md is deleted by default unless you confirmed the product genuinely calls a model. A file that outgrows one topic gets split into its own subdirectory.

4

Spec now, code later

This pass produces the spec, not the app. Building the real backend against it is a separate, later ask — BUILD-ORDER.md then runs its own phase order (infrastructure first, domain logic later), which is close to the reverse of the interview's order on purpose: one is optimized for what's safe to ask about, the other for what's safe to build against.

Reference: the backend files

What the agent actually writes into backend/rules/, plus the two procedure files that drive the interview and the build. This is the vocabulary the tutorial below uses.

rules/data-models.mdInterview file 1

Every table: columns, keys, and constraints, plus what's computed instead of stored. Also settles primary-key strategy (sequential vs. UUID), the soft-delete-vs-hard-delete convention, and foreign-key delete behavior — schema-level decisions most other files build on, so it's asked first.

rules/business-logic.mdInterview file 2

The actual algorithms and formulas behind the product's defining mechanism, in enough procedural detail that two engineers would build the same thing. Where pricing/charging rules and race-safety on any shared resource live, if money moves through the system. If there's no real mechanism, this file says so plainly instead of inventing one.

rules/auth.mdInterview file 4

Sign-in method, session mechanics (session-based vs. JWT, token transport, refresh-token rotation), roles, the password-reset flow, and how account deletion actually behaves against shared or owned data.

rules/api-routes.mdInterview file 5

Every route, grouped by purpose, with its request shape and the specific error cases a client needs to branch on. Cross-references business-logic.md instead of re-explaining the logic inline.

rules/error-handling.mdInterview file 6

The one response envelope and status-code table every route uses, plus a global exception handler that never leaks a raw stack trace to the client — decided once, here, instead of every route improvising its own shape.

rules/security-practices.mdInterview file 7

Rate limiting, input validation, query safety, mass-assignment protection, row-level security policies, CORS/CSRF, and file uploads — the cross-cutting protections layered on top of auth and the routes.

rules/engineering-standards.mdInterview file 8 — stack decided here

Stack, project structure, and deployment, reasoned from everything the interview surfaced earlier rather than picked by default. Also backups/disaster-recovery, secrets management, and payment/email providers where relevant.

rules/observability.mdInterview file 9

Correlation ids, structured logging, real error tracking, metrics on this product's own easy-to-get-wrong failure modes, and the two health-check routes a hosting platform needs for a safe deploy.

rules/testing.mdInterview file 10

The test pyramid scoped to this specific product, an explicit row-level-security-role callout if RLS is used, and what actually runs in CI versus what only runs on merge.

rules/llm-integration.mdOptional — interview file 3

Deleted by default. Kept only if the product genuinely calls an LLM: the model-owns-conversation / backend-owns-every-write rule, tool design, and a separate eval suite that never gates a normal pull request.

INTERVIEW.mdProcedure

The ordered interview itself — which question gets asked when, and why nothing is asked before what it depends on. Not part of the product's spec; this is what drives the agent through the files above.

BUILD-ORDER.mdProcedure

The phase order for actually building the backend once you separately ask for real code — infrastructure first, domain logic later, close to the reverse of the interview's order and explained as such.

Tutorial: build TaskFlow, a small CRUD API

One example, start to finish — a tiny personal task tracker. Every answer below is a plausible real answer, so you can see the shape of the finished spec, then the finished API.

1

Prerequisites

An empty project folder, and a coding agent (Claude Code or otherwise) you can start a session in. Nothing else — no database running yet, no framework chosen yet.

2

Install

From inside that empty folder:

macOS · Linux · git-bash · WSL 
curl -fsSL https://raw.githubusercontent.com/DMK980/Blueprints/main/install.sh | bash -s -- backend
3

Run the interview

Start a session and let it interview you. The root phase resolves fast for something this small:

What does this product do?
A personal task tracker. One user type — you sign in and manage your own list of tasks: add one, mark it done, edit it, delete it.
Is there a defining mechanism?
No — plain CRUD, no ranking, no matching, nothing algorithmic. Say so plainly rather than inventing drama that isn't there.
Roles beyond a plain user?
None.
Does money move through this system?
No.
Does it call an LLM?
No — llm-integration.md gets deleted.

Then each file, in order. Highlights:

data-models.md — what entities?
Just one: tasks. Each task belongs to exactly one user — no sharing, no collaboration.
data-models.md — primary keys?
UUID. There's no reason to let anyone guess how many tasks exist by incrementing an id.
data-models.md — soft or hard delete?
Hard-delete. Nothing else ever references a task, so there's nothing a soft-delete would protect.
auth.md — sign-in method?
Email + password. No OAuth, no magic link — keep it simple.
auth.md — session-based or JWT?
Session-based. A handful of users, no scaling pressure, and instant revocation on logout is worth more here than avoiding a lookup.
api-routes.md — user-facing actions?
Create a task, list my tasks, get one, update one, delete one. Five verbs, five routes.
security-practices.md — any shared tables?
None — tasks is strictly owned, so row-level security is a plain owner_id = current_user_id policy.
engineering-standards.md — the stack?
Node.js + Express, PostgreSQL. Nothing above needed vector search, real-time updates, or background jobs — a small service is genuinely sufficient here, not a default.

Everything else (business-logic, error-handling, observability, testing) resolves quickly too — there's no real algorithm to document, just the shared error envelope, request logging, and a couple of concurrency-free test cases.

4

What you get

Short excerpts of the real generated spec for this example:

rules/data-models.md (excerpt)
### tasks
id          uuid, pk           — not sequential, nothing to probe by guessing
owner_id    uuid, fk users.id  — on delete: cascade (a task has no meaning without its owner)
title       text, not null
completed   boolean, not null, default false   — stored, nothing to derive it from
created_at  timestamptz, not null, default now()
updated_at  timestamptz, not null

Hard-delete only. No deleted_at — nothing else ever references a task.
rules/api-routes.md (excerpt)
### Tasks
POST   /tasks       create a task for the caller
GET    /tasks       list the caller's own tasks
GET    /tasks/:id   404 if it isn't the caller's
PATCH  /tasks/:id   update title/completed — 404 if it isn't the caller's
DELETE /tasks/:id   404 if it isn't the caller's
5

Build it

A separate, later ask — "now build the real backend." The agent works through BUILD-ORDER.md's phases, one at a time, applied to this example:

  1. 01Scaffold — an Express app, a Postgres connection, the test/CI harness.
  2. 02Observability — a request-id middleware, structured logs, /healthz and /readyz.
  3. 03Error handling — one JSON error envelope, one global exception handler.
  4. 04Data models — the tasks migration.
  5. 05Auth — signup/login/logout, session cookie.
  6. 06Security — the row-level-security policy on tasks, a login rate limit.
  7. 07Business logic — nearly nothing here; a couple of input checks, tested directly.
  8. 08Routes — the five task routes, wired to auth, the RLS policy, and the shared error envelope.
6

Try it

What you're left with is a real, working CRUD API:

shell
$ curl -c cookies.txt -X POST localhost:3000/auth/signup \
    -d '{"email":"you@example.com","password":"correct-horse"}'

$ curl -b cookies.txt -X POST localhost:3000/tasks \
    -d '{"title":"Write the docs page"}'
{"id":"9f2a...","title":"Write the docs page","completed":false}

$ curl -b cookies.txt localhost:3000/tasks
[{"id":"9f2a...","title":"Write the docs page","completed":false}]

$ curl -b cookies.txt -X PATCH localhost:3000/tasks/9f2a... \
    -d '{"completed":true}'
{"id":"9f2a...","title":"Write the docs page","completed":true}

$ curl -b cookies.txt -X DELETE localhost:3000/tasks/9f2a...
